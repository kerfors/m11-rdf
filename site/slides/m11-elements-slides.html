The row contradicts itself: its code is the primary objective, its condition the secondary.

The Specification has a heading here, not an element: {3.2.X Secondary Objective <#>}, H, “Concept: Heading”. The exploratory objective heading has the same pattern (HL7 149, CDISC 153).

Narrative elements: one attribute, told apart by a section number

NarrativeContentItem.textsectionNumber = <desired section>

277 mapping statements, for 140 elements, point at the same USDM attribute. Only the condition tells them apart, and a section number is a string in the study file.

m11-rdf gives each of the 160 sections a global identifier; 111 Template headings are themselves an element.

And for the field on slide 4: in { } in the Template, Required in the Specification. 4 fields linked to an element are like this.

m11-rdf keeps each statement as published, flags it, and lists the rest in its build reports (d2-residue.csv, d5-residue.csv). It does not repair them, and it does not judge which source is right.

Needs a convention

Content that points at its element

277 statements, for 140 elements, reach USDM only as NarrativeContentItem.text plus a section-number string.

A study file needs a way to say: this content is that M11 section or element. Neither USDM v4 nor the mappings have one yet.

m11-rdf applies mechanical, reproducible rules only. Where a rule would need judgement (a near-match of names, a choice between subclasses, a repaired spelling), the row stays in the residue.

Questions to ask of the alignment with ICH M11

Coverage

55 of the 270 elements have no mapping statement. Do they get a place in USDM?

Document content

Can content point at an M11 section or element, rather than at a section number written as text?

Model and mapping

160 rows in each mapping name StudyProtocolDocumentVersion, which USDM v4.0.0 does not have (it has StudyDefinitionDocumentVersion). Is the model changed, or the mapping?

Step 4

The CDISC mapping is stated against the M11 Step 2 draft. For 39 of the 284 section and element-name pairs that both files have, the NCIt code differs.

Codes and names

Where m11-rdf finds a CNEW row by its name (HL7 128, CDISC 154), the element's code is published in the ICH M11 Terminology. Codes in the cells, and names as in the Specification, would make the mapping resolve by code.

When 4.1 is published, m11-rdf is rebuilt against it: the same element identifiers, new USDM and mapping inputs, and the difference per element.
